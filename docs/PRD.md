## 1. 目标与约束

### 1.1 真实目标

帮助毕业旅行组织者把分散的成员意向，整理成可执行、可分享、可结算的旅行计划。核心价值是减少反复问询、暴露分歧并推动达成共识。

核心路径：收集成员偏好 → 比较方案 → 确认出行 → 调整日程 → 记录支出 → 结清费用。

### 1.2 成功标准

- 评审者无需登录，即可通过公开链接进入并体验完整示例。
- 修改成员时间或预算后，能立即看到候选方案的适配变化和原因。
- 时间、预算有冲突时，明确显示受影响成员，并提供有依据的调整方向。
- 支持部分人参与和不同金额分摊，能得出准确的个人余额与转账建议。
- 创建、修改、刷新、导出、导入形成完整数据闭环。
- 桌面和手机均可完成核心任务；性能与上线验收见开发文档。

以上为验收目标，不代表已经获得真实用户验证。首轮可用性验证目标：首次体验者在 5 分钟内完成“改预算、选方案、记费用、看结算”，无需开发者解释。

### 1.3 已确定的约束

- 部署使用 GitHub Pages；第一版无自建服务器、数据库和账号系统。
- 本地数据是当前设备、当前浏览器中的工作副本，不是云端协作文档。
- 跨设备使用计划快照、邀请/反馈文件或链接、完整备份传递数据；不承诺实时同步。
- 最终提交一个公开且保持稳定的部署链接；不在迭代过程中更换仓库名或域名。
- 目的地与费用为内置估算模板，不提供实时票价、酒店库存或预订。
- AI 用于辅助开发，MVP 不依赖在线大模型 API。

## 2. 用户与场景

| 用户 | 主要任务 | 当前困难 |
| --- | --- | --- |
| 组织者 | 收集意向、比较方案、安排日程、维护账本 | 群消息分散，需要反复统计 |
| 成员 | 填写时间预算、表达意向、查看计划与应付费用 | 不清楚方案是否适合自己、费用如何得出 |
| 评审者 | 快速判断产品价值并验证功能 | 空白页或过长流程难以体验 |

“组织者”和“成员”是产品操作视角，不是经过认证的身份或权限角色。成员视角切换仅存在于示例体验，明确标注为演示。

主要场景：4～12 人的小队，由组织者维护最终版本。MVP 支持每个旅行最多 20 人、同一浏览器最多 10 个旅行；超出范围及时提示。

## 3. 产品结构

### 3.1 入口与导航

- 首次打开直接展示可操作的示例旅行，不弹长引导；保留“创建旅行”入口。
- 有本地旅行时，默认恢复最近访问的旅行和工作区。
- 桌面以侧边导航切换“小队、方案、日程、账本”；手机提供四个短标签入口。
- 顶部提供旅行切换、分享、导出与更多操作；当前旅行状态在内容区自然呈现。
- 新建旅行只要求名称；成员、预算、日期可后补。缺少信息时引导补齐必要字段。

### 3.2 四个工作区

| 工作区 | 核心内容 | 主操作 |
| --- | --- | --- |
| 小队 | 成员、出发地、预算上限、可用日期、偏好、资料完整度 | 添加/编辑成员，邀请填写，导入反馈 |
| 方案 | 日期选择、候选目的地、估算明细、约束匹配、成员意向 | 比较、修改估算、确认方案 |
| 日程 | 按天活动、时间与类别、人均预计支出 | 新增、编辑、删除、上下移动 |
| 账本 | 实际费用、垫付人、参与人、分摊、余额和转账建议 | 记一笔、查看计算、记录结算 |

不建立独立营销首页，不用重复说明文字占据主要操作空间。必要说明仅用于估算来源、本地保存、分享范围和错误恢复。

## 4. MVP 功能要求

### F01 旅行与成员管理（P0）

- 创建、切换、重命名和删除旅行；删除旅行需确认并提供先导出入口。
- 成员资料包含昵称、出发城市、预算上限、可用日期区间、偏好标签。
- 尚未填写的字段保留为“待补充”，不能按零预算或无限可用处理。
- 昵称允许重复，以唯一 ID 区分；界面使用城市等已有信息辅助识别。
- 已被实际账目引用的成员不能直接删除，显示涉及的记录入口。

验收：添加成员并刷新后仍存在；不完整资料不会被显示为“全部适合”；删除受引用成员有明确反馈。

### F02 候选方案与共识（P0）

- 内置至少 6 个目的地模板，覆盖海边、城市、人文、自然等偏好。
- 选择出发日期和 2～5 天时长，生成可比较的候选方案。
- 每个方案展示目的地、日期、成员个人基准估算的最低～最高值、时间匹配人数、预算可接受人数和资料缺失人数。区间反映出发地差异，不是价格波动预测；每人仍使用明确金额参与预算判断。
- 进入详情可看到成员逐人适配、交通/住宿/餐饮/活动/机动预算明细，以及估算假设。
- 允许组织者调整估算参数，查看适配变化；不把修改估算当成实际降价承诺。
- 成员对方案表达“赞成、可接受、不参加”；未反馈单独展示。
- 时间和预算属于硬约束；偏好仅用于可行方案之间的排序。
- 正常确认要求资料完整、全员满足硬约束、全部成员选择赞成或可接受。
- 不能以多数票绕过某个成员的预算、时间或“不参加”。组织者可回到小队调整出行成员，重新确认。

验收：降低一名成员预算后，相关方案显示冲突并调整排序；无共同日期时展示冲突，不伪造可行方案。

### F03 确认与日程（P0）

- 确认方案后按目的地模板生成按天日程，不重复追加已有项目。
- 日程条目包含日期、可选起止时间、名称、类别、费用归属、人均预计活动支出和可选备注。交通、住宿、餐饮安排可仅记录信息，已计入方案的费用不重复加入活动预算。
- 支持上下移动，同一天有时间的活动按时间展示，未定时间的活动保留手动顺序。
- 时间重叠提示，非法起止时间阻止保存。
- 成员、日期、预算或方案估算变化后，原确认标记为失效，保留已编辑日程。
- 手动修改活动不擅自覆盖候选方案估算；日程预算与方案基准差异需要可见。
- 重新确认后由用户选择保留或替换日程；替换前展示影响并二次确认。

验收：确认生成一次日程；再次确认不产生重复；修改预算后确认失效但手工日程保留。

### F04 账本与结算（P0）

- 每笔费用指定金额、日期、类别、垫付人和参与成员；单笔由一人垫付。
- 支持参与人均摊和自定义金额，垫付人可以不属于参与人。
- 展示每人已付、应承担、已结算与当前余额，并可展开来源。
- 根据当前余额生成确定性的转账建议；不宣称数学上全局最少笔数。
- “记录已转账”只记录线下确认，不调用支付、不证明真实到账。
- 已有结算记录时锁定原费用编辑；更正路径见业务规则。

验收：非参与人不承担费用；分摊总额等于原账单；记录结算后余额正确变化；全额结清后不再建议转账。

### F05 静态分享与反馈（P0）

提供三种明确不同的传递方式：

| 方式 | 内容 | 接收方操作 |
| --- | --- | --- |
| 计划快照 | 目的地、日期、公开日程、估算总览，不含成员私人资料或实际账单 | 只读查看，或另存为新旅行 |
| 单成员邀请 | 此成员填写所需的旅行上下文、日期窗口、候选方案和标识 | 填写偏好与方案意向，生成反馈链接或文件 |
| 完整备份 | 全部本地旅行业务数据，包括成员和账本 | 手动导入成为本地副本 |

- 反馈需组织者粘贴链接或选择文件，预览差异后应用到对应成员。
- 导入校验所属旅行、版本、目标成员、重复或过期反馈；不静默覆盖。
- 链接是生成时的快照，没有自动更新、服务端权限或撤回能力。分享面板简短说明范围。
- 链接过长时提供文件导出；剪贴板不可用时可手动复制。
- 保存失败不得显示“已保存”；提供重试及导出当前内存数据入口。

验收：用另一个浏览器窗口完成“邀请 → 填写 → 回传 → 导入”，原旅行仅在组织者应用后变化。

### F06 示例与空状态（P0）

- 示例包含 6 位虚构成员、可解释的冲突、至少 3 个可比较方案、日程和示例费用。
- 示例使用相对当前日期生成的未来时间，避免过期导致演示不可用。
- 示例可编辑、可刷新保留，可单独重置；重置不影响用户创建的旅行。
- 示例的成员视角、意向和账目均明确属于虚构演示，不展示虚假在线状态。
- 空状态提供当前需要的操作，不使用大段介绍。

## 5. 完整演示脚本

1. 打开示例旅行，看到小队成员与当前约束。
2. 将一位成员预算从 ¥1,500 改为 ¥1,100，看到原方案不再满足该成员。
3. 修改住宿估算或选择较低预算方案，查看具体成本差异。
4. 在示例成员视角完成意向，组织者确认全员满足的方案。
5. 在日程中添加一个活动，观察日程预算与原估算的差异。
6. 新增 ¥100 的三人均摊费用，查看分到分的承担明细。
7. 查看转账建议，记录一笔线下转账，观察余额变化。
8. 刷新后数据保留；导出备份并在干净浏览器导入。

## 6. 第一版不做的内容

- 登录注册、身份验证、实时聊天、自动跨设备同步。
- 面向陌生人的公开招募广场与人员匹配。
- 实时机酒比价、地图导航、下单、收款和真实支付。
- 真实在线 AI、自动获取个人定位、第三方账号授权。
- 多币种、汇率、退款流水、多人共同垫付一笔账单；共同垫付可拆成多笔处理。
- 自动最优路线和复杂拖拽排程；使用可访问的上下移动完成基础调整。

以上不进入首轮开发排期。若后续新增后端，需要重新定义真实权限、同步冲突、身份验证和数据保留策略。

## 7. 交付与验收

- 页面必须是可交互的应用，不只是一张产品展示页。
- P0 均为本次 MVP 必须完成项，包含静态反馈闭环，不在开发时默认为可选。
- 规则、计算和异常以业务规则文档为准；实现、测试、性能与发布以开发文档为准。
- 交付物：源码、锁文件、自动发布配置、可复现的检查命令、公开稳定链接与实际验收记录。
- 当前仓库仅有文档，本文不代表已经开发、部署或通过验收。
