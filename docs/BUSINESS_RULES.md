# 同路 · 毕业旅行业务规则

版本：MVP v1.0  
日期：2026-11-17  
适用范围：[PRD](./PRD.md) 中全部 P0 功能  
实现与验收：[MVP 开发文档](./MVP_DEVELOPMENT.md)

本文规定同一输入应产生的业务结果。实现不得通过界面中的临时判断绕过这些规则。

## 1. 名词与基础约定

| 名词 | 定义 |
| --- | --- |
| 旅行 | 成员、方案、日程、费用和结算的本地工作集合 |
| 成员 | 唯一 memberId 对应的一位计划参与者，昵称不是主键 |
| 方案版本 | 某个候选方案的日期、目的地和估算参数的一次确定版本 |
| 约束版本 constraintRevision | 影响邀请、适配或确认的一组输入的版本号 |
| 内容版本 revision | 旅行每次成功业务变更后递增的版本，用于保存和备份冲突判断 |
| 意向 | 成员针对某方案版本的赞成、可接受或不参加 |
| 确认 | 全员符合条件时对当前方案与约束版本的确认记录 |
| 实际费用 | 已发生、需要分摊的人民币支出 |
| 结算记录 | 用户手工确认的成员之间的线下转账记录 |

- 所有 ID 使用稳定唯一标识，排序使用 ID 的代码单元字典序，不依赖昵称或区域排序。
- MVP 仅人民币。持久化金额单位为分，全部为安全整数；界面单位为元。
- 日期采用 `YYYY-MM-DD`，日期运算按公历自然日，不把日期字符串经 UTC 转换后当作本地日期。
- 时间采用 `HH:mm`，均按本次旅行的中国当地时间理解；不支持跨时区排程。
- 审计时间使用 ISO 8601 时间戳，仅用于展示，不能代替版本进行冲突判断。
- 昵称 1～20 字，旅行名 1～40 字，活动/费用名称 1～60 字，备注最多 300 字；去除首尾空白后验证。
- 每旅行最多 20 人、20 个方案、100 个活动、200 笔费用、200 条结算记录。最多保存 10 个旅行。
- 文本作为普通文本展示，不接受 HTML、脚本或可执行模板。

## 2. 成员与资料

### BR-01 资料完整度

成员用于适配计算的必填信息为：昵称、出发城市、预算上限、至少一个可用日期区间。偏好标签可为空，表示无特别偏好。

- 预算合法范围：¥0～¥100,000；零预算是明确值，空值表示未知。
- 每位成员最多 5 个日期区间，起止均包含当天；起日不得晚于止日。
- 重叠或相邻日期区间合并，再用于共同日期计算。
- 资料缺失的成员为“待补充”，不能归为匹配，也不能归为明确冲突。
- 适配必须展示匹配、冲突、未知三种状态，不以缺失资料提高适配率。

### BR-02 成员变更

- 添加或删除成员、改变必填资料或偏好，均增加 constraintRevision，重新计算适配。
- 相同值重复保存不增加版本。
- 已有实际费用的垫付人、参与人，以及结算记录的转出/转入人不可删除，包括已撤销结算中保留的引用。
- MVP 不提供临时隐藏成员来绕过确认。确定不参加的成员需在无账目引用时正式移出小队。
- 不支持成员合并或 ID 重用；重复昵称不会合并记录。

## 3. 时间与候选方案

### BR-03 共同出行日期

- 旅行可设置搜索窗口，默认未来 90 天，最长 180 天；出行时长 D 为 2～5 个自然日。
- 某成员匹配方案，当且仅当 `[出发日, 出发日 + D - 1]` 完整包含在其某个合并后的可用区间内。
- 不能将两段中间有空白的区间拼接成连续出行日期。
- 共同日期为所有资料完整成员可出行日期的交集；只要存在资料不完整成员，结果标记“待补全后确认”。
- 候选共同出发日按日期升序返回，最多显示前 10 个；用户可以在搜索窗口内另选日期查看冲突。
- 无共同日期时返回空集合，并允许查看某个指定日期逐人的冲突原因；不自动排除成员。
- 新确认的出发日期不得早于操作当天；过去旅行可查看、记账和结算，不可重新确认为未来计划。

例：A 可用 7 月 1～5 日，B 可用 7 月 3～6 日，D=3，仅 7 月 3 日出发同时满足两人。

### BR-04 目的地和费用估算

每个模板记录标签、支持时长、活动种子及估算来源说明。估算统一使用明确的整数分参数：

```text
成员 i 的人均基准估算 E_i =
  该成员出发城市至目的地的往返交通估算 T_i
  + 每晚人均住宿 H × (D - 1)
  + 每天人均餐饮 F × D
  + 人均活动总额 A
  + 人均机动预算 R
```

- H 已经是人均值，不再次除以成员数；MVP 不做房间余位与房型组合算法。
- T_i 由内置城市交通表查找；没有对应城市时，该成员费用为未知，需组织者手动补入交通估算。
- 手工交通估算绑定成员及其出发城市；成员改变城市后旧值不再适用，重新查表或要求补充，不沿用上一城市的值。
- 不允许把未知交通当作 0 元。缺少 T_i 时该方案不能通过全员确认。
- 参数非负、精确到分，E_i 不得超过 ¥100,000。方案组均值仅作展示，不替代个人约束判断。
- 卡片显示人均最低～最高估算；所有人的 E_i 相同则显示单一金额。资料缺失时注明估算未完成。
- 若展示均值，对分取四舍五入；预算比较始终使用个人未平均的 E_i。
- 模板价格标记“内置估算，非实时报价”；不得显示虚构抓取时间、折扣或实时库存。
- 建议降低住宿或更换交通，仅在已有参数可以算出变化时给出差额；否则提示手动调整估算，不伪造节省金额。

### BR-05 匹配与排序

针对每位成员分别计算时间和预算状态：

```text
时间通过：完整覆盖出行日期
预算通过：E_i <= budgetCap_i
硬约束通过：资料完整，且时间通过、预算通过
明确冲突：至少一个已知硬约束失败
待补充：没有已知失败，但仍缺必要信息
```

人数以成员 ID 去重；时间冲突人数与预算冲突人数可能重叠，不能相加当作总冲突人数。

偏好适配：有偏好成员的分数为 `交集标签数 / 该成员偏好标签数`；无偏好成员不参与平均，全部无偏好时偏好分为 0。

排序采用以下元组依次比较：

1. 全员硬约束通过的方案排在前面。
2. 其余方案按“存在明确冲突的不同成员数”升序。
3. 再按“待补充的不同成员数”升序。
4. 再按偏好平均分降序。
5. 再按全员估算合计升序；缺少个人估算的方案该项视为正无穷。
6. 再按出发日期升序、方案 ID 升序。

不把这些结果包装成未经验证的“AI 匹配百分比”。详情展示实际人数和原因。

## 4. 意向、确认与版本

### BR-06 意向有效性

- 意向值为 `approve`（赞成）、`acceptable`（可接受）、`decline`（不参加）；缺记录表示未反馈。
- 意向绑定 `memberId + planId + planVersion + constraintRevision`，同组合只保留一条当前记录。
- 改变约束版本后旧意向保留为历史，但不再用于当前确认。第一版不自动继承旧意向。
- 组织者可根据线下沟通代录，记录来源为 `organizer`；邀请反馈来源为 `feedback`，示例操作为 `demo`。
- 上述来源是可追溯说明，不代表身份认证。导入外部反馈不能证明由本人提交。

### BR-07 确认条件和失效

同时满足以下条件才可确认：至少 2 位成员；所有资料完整；候选费用完整；日期有效；全员硬约束通过；所有人当前意向为赞成或可接受。

- 确认保存 planId、planVersion、constraintRevision 和确认时间。
- 修改成员、搜索窗口、D、候选方案集合，或任一方案的日期、目的地、估算参数，增加 constraintRevision。修改具体方案还增加该方案 planVersion。
- 对全部意向统一失效是 MVP 的保守策略，防止旧反馈针对不同候选上下文被误用。
- 当前确认方案中任意成员意向改为“不参加”或被清空，确认立即失效；不增加 constraintRevision。
- 旅行重命名、日程编辑、实际记账、结算不增加 constraintRevision。
- 派生状态只有“筹备中、已确认、待重新确认”：从未确认为筹备中；确认快照与当前输入一致且条件仍满足为已确认；其他存在历史确认的情形为待重新确认。
- 状态按数据重新求值，不允许用户直接写入“已确认”。

### BR-08 日程与估算关系

- 首次确认生成模板日程；未确认前也允许手工建立草稿日程。
- 再次确认时有日程则默认保留；替换属于显式操作，不能自动覆盖手工内容。
- 活动日期必须在当前日程所绑定的旅行日期范围内。更改方案日期后保留旧日程，标出范围外活动，要求调整后才可导出为正式计划快照。
- 同日的有时间活动按起始时间、手动顺序、ID 排序；无时间活动排在其后，按手动顺序、ID 排序。
- 起止时间可以同时为空；填写一个时必须填写另一个，结束必须晚于开始。跨午夜活动需拆为两条。
- 时间重叠仅提示，不阻止保存；按半开区间判断，10:00 结束与 10:00 开始不算重叠。
- 日程条目的费用归属为 `activities`（计入活动预算）或 `included`（已含在方案其他分项，仅记录安排）。included 条目金额固定为 null，界面标明“费用已含于方案”，不显示为待估算。
- activities 条目的金额为“人均预计活动支出”，允许 0，允许未估算；未估算不能计为已知零费用。新增交通、住宿、餐饮类别默认 included，其他类别默认 activities，用户可明确调整归属。
- 设 activities 条目的已知金额之和为 S，逐人修订估算为 `E'_i = E_i - A + S`，即用日程活动替换方案的活动分项，不重复叠加。存在未知 activities 金额时修订估算标记未完成；included 条目不参与 S。
- 确认判断采用方案 E_i；E'_i 超预算时在日程提示，分享快照显示当前差额和确认状态，不能暗示新日程已获全员同意。
- 日程变化不生成实际费用；记账也不回写估算。二者在界面中分开呈现。

## 5. 实际费用与分摊

### BR-09 输入和均摊

- 单笔金额 > 0 且不超过 ¥100,000。仅接受最多两位小数的十进制金额文本；拒绝负数、指数、NaN 和无穷值。
- 用十进制文本拆分为分，不使用浮点乘法后截断进行金额解析。
- 每笔一名垫付人、至少一名参与人，参与人不重复且都属于本旅行。
- 垫付人可以不参与消费，仍取得相应应收余额。
- 均摊金额 A 分，N 位参与人：每人先分配 `floor(A/N)`，余数按参与人 ID 升序依次每人加 1 分。
- 界面保留正常成员顺序，但明确展示最终分配金额；编辑均摊参与人后重新计算并在保存前展示。

例：10000 分分给 ID 升序的 a、b、c，分别为 3334、3333、3333 分。

### BR-10 自定义金额

- 每位参与人分摊金额为非负整数分，允许其中某人为 0；所有参与人的金额之和必须严格等于原账单。
- 未填写分摊不能自动补成 0；剩余差额显示为待分配。
- 自定义模式不自动修正差额，不按比例偷偷缩放。
- 单笔费用保存其最终分摊明细，不在后续成员列表排序变化时重新分配历史尾差。

### BR-11 余额与不变量

对成员 i：

```text
P_i = 其垫付的实际费用总额
O_i = 其承担的实际费用总额
B_i = P_i - O_i + 已转出结算总额 - 已转入结算总额
```

- B_i > 0 表示当前应收；B_i < 0 表示当前应付；B_i = 0 表示结清。
- 每笔费用 `sum(allocations) = amount`。
- 全旅行 `sum(P_i) = sum(O_i)`，且 `sum(B_i) = 0`。
- 统计金额必须保持安全整数；超过 `Number.MAX_SAFE_INTEGER` 的输入或累计结果拒绝保存。
- 空账本全部为 0，显示“暂无费用”，不生成虚构转账建议。

### BR-12 转账建议与记录

1. 将负余额成员按欠款绝对值降序、ID 升序排列；正余额成员按应收降序、ID 升序排列。
2. 从双方首位开始，建议转账 `min(欠款额, 应收额)`。
3. 从剩余额中扣除，余额归零的一方向后推进，直到全部为 0。

同一输入产生同一建议；这是减少操作的确定性算法，不承诺全局最少笔数。

- 点击“记录已转账”前展示转出人、转入人、金额，用户确认后创建结算记录。
- 只能从当前负余额成员转给正余额成员；金额不得超过双方当前剩余额；同一人不能转给自己。
- 发送方 B 增加转账金额，接收方 B 减少，方向不可反转。
- 保存采用命令 ID 去重，连点或重复提交不得创建两条结算。
- 不实现支付，不显示“银行到账成功”等未经验证的状态。
- 有任一有效结算记录时禁止新增、修改、删除实际费用。更正费用前必须明确确认“撤销全部有效结算记录”；撤销仅改变本地账本，真实线下转账不会被撤回。撤销后原转账需按真实情况重新录入。
- 单条误记结算也通过“撤销全部结算后重录”更正，避免局部撤销使后续记录不再满足原先的方向约束。
- 被撤销记录保留但不参与计算，不能再次激活。旅行不设不可逆的“最终结清”锁。

验算：A 垫付 ¥300 三人均摊，B 垫付 ¥90 且仅 A、B 参与，则 A/B/C 余额为 +¥155、-¥55、-¥100。C→A ¥100 后为 +¥55、-¥55、¥0；B→A ¥55 后全部为 0。

## 6. 邀请、分享与导入

### BR-13 传递协议

全部载荷包含 `schemaVersion=1`、type、payloadId、createdAt 和 body。只接受已支持的类型与字段白名单，不执行载荷文本。

| 类型 | 必要内容 | 排除内容 |
| --- | --- | --- |
| snapshot | 名称、确认状态、选定方案公开估算、日程、生成时间 | 成员列表、个人预算/可用日期、备注、实际费用、结算、反馈历史 |
| invitation | tripId、目标 memberId 和昵称、constraintRevision、搜索窗口、D、候选 id/version/名称/标签/日期及估算参数和填写说明 | 其他成员资料、账本、私密备注；目标成员预算和可用日期不预填分享，专属交通值按下述规则选择性附带 |
| response | invitationId、tripId、memberId、基准 constraintRevision、成员资料和候选意向 | 账本、其他成员资料、任意业务对象修改指令 |
| backup | 完整单个旅行、schemaVersion、导出时间 | 应用缓存、其他旅行、运行时 UI 状态 |

- snapshot 只包含所选方案；草稿快照允许生成但必须标记“未确认”。日程超出该方案日期时阻止生成并定位待调整项目。
- public 活动不包含可选备注。确认状态只代表生成时刻，不代表打开时刻仍有效。
- snapshot/invitation/response 均支持 JSON 文件；链接采用 UTF-8 JSON 的 Base64URL 编码，放在 URL fragment 中。
- 整个 URL 的 UTF-8 长度上限为 8000 字节，这是产品保守阈值，不是所有平台的链接兼容保证。超过后只导出文件。
- 编码不是加密；链接持有者可读其全部内容，无法可靠撤回。分享前展示范围，不把私人数据默认带入。
- invitationId 在组织者本地登记，包含基准版本和目标成员，反馈必须对应一个登记的邀请。
- 邀请只传递共用估算参数，不传完整 transportByMember 映射；成员填写城市后在接收端查同版交通表。若存在目标成员专属手工交通估算，可在分享范围确认后附带该成员的城市与金额；不包含其他人的交通数据。填写新城市后该专属值不再适用。邀请携带估算模板版本，接收端不支持该版本时只能查看，不提交意向，要求组织者重新生成邀请。

### BR-14 反馈应用与冲突

- 检查 schema、大小、tripId、invitationId、memberId、方案 id/version 和字段合法性；不匹配则拒绝。
- 当前 constraintRevision 必须与邀请基准一致；否则反馈标记过期，允许只读查看与重新发邀请，不允许强制覆盖。
- 相同 response payloadId 重复导入为无操作，不增加任何版本。
- 相同邀请产生的新 payloadId 视为重新提交：展示旧值、新值和已导入记录，用户显式选择后才能替换；同样要求基准版本仍有效。
- 反馈未改变成员资料时，可仅写入当前版本意向，不增加 constraintRevision。
- 反馈改变约束资料时：原子写入资料 → constraintRevision 加 1 → 所有旧意向失效 → 将此次反馈中的方案意向写入新约束版本。候选方案本身的版本不变。
- 一名成员更新资料会使其他未回传邀请过期。MVP 接受这一保守限制；组织者应先完成资料收集，再统一发一轮方案意向邀请，不悄悄跨版本合并。
- 预览阶段不修改任何数据；应用成功才登记 responseId。整体校验失败不得部分写入。
- 提示语为“已应用到此设备”，不显示“已同步到所有成员”。

### BR-15 快照与备份导入

- 打开快照默认只读且不写本地旅行；另存时生成新的 tripId，重新映射实体 ID，不继承原邀请、意向、确认或账本。
- 备份包含私人资料，导出前提示范围。MVP 每次导出一个旅行，不自动上传。
- 备份导入先校验完整引用、金额、版本和不变量，再预览名称、成员数、日期、费用数。
- 本地不存在 tripId 时可导入为新本地旅行；存在同 ID 时默认另存副本并重新映射 ID、清除邀请/反馈应用登记，不做字段级合并。
- 同 ID 的覆盖必须明确确认，先保留旧版恢复副本；导入版本较旧时额外显示版本差异。旧版恢复副本与替换内容一起原子持久化，容量不足则不覆盖。
- 完整备份作为同一旅行恢复时保留账本、意向与确认；另存副本时保留财务数据与有效内部引用，清除意向和确认，避免冒充原共识。
- 未支持的更高 schemaVersion 拒绝导入，保留文件，不尝试猜测字段意义。
- 文件上限 1 MiB；解码后的链接 JSON 也不得超过 1 MiB。超限、损坏或非法引用均不产生本地变更。

## 7. 保存、恢复与异常

### BR-16 保存事务

- 完整校验通过后，每个业务命令只提交一次状态，revision 加 1，持久化完整有效旅行。
- 表单草稿不算成功保存，不增加业务版本；保存按钮提交期间禁止重复提交。
- 写入失败时保留原持久化版本和当前内存状态，显示“尚未保存”并允许重试/导出。不得刷新页面来假装恢复成功。
- 本地解析失败时不自动删除原字符串或覆盖示例。提供下载损坏数据、从备份恢复或明确确认后重置入口。
- 清除浏览器数据、隐私模式结束、换浏览器或站点路径/来源变化，都可能使原本地工作不可见；不承诺永久保存。
- 同源多标签页发生外部写入时，旧页面阻止继续提交，提示重新载入或导出当前内容；MVP 不提供多标签页实时编辑合并。

## 8. 必须覆盖的规则样例

| 编号 | 输入/操作 | 预期结果 |
| --- | --- | --- |
| R01 | 某成员预算为空 | 待补充，不能全员确认 |
| R02 | 预算刚好等于个人估算 | 预算通过 |
| R03 | 2 段日期之间有 1 天空白 | 不可跨空白组成连续旅行 |
| R04 | 一人同时有时间和预算冲突 | 总冲突人数只计 1 人 |
| R05 | 100 元三人均摊 | 33.34、33.33、33.33，总计 100 |
| R06 | 自定义分配合计少 0.01 元 | 阻止保存并显示待分配差额 |
| R07 | 垫付人不参与消费 | 已付增加，应承担为 0 |
| R08 | 已结算后编辑费用 | 阻止，给出撤销全部结算路径 |
| R09 | 过期邀请回传 | 只读预览，不应用 |
| R10 | 相同反馈或结算重复提交 | 不重复修改余额、版本或资料 |
| R11 | 导入引用了不存在成员的费用 | 整体拒绝，不部分导入 |
| R12 | 当前活动金额未知 | 日程估算未完成，不当成零费用 |
| R13 | 生成分享 | 默认不包含个人预算和实际账目 |
| R14 | 修改已确认方案预算 | 确认与旧意向失效，日程保留 |
